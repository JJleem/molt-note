# ADR-0012 — 온라인 회의 녹음은 **Core Audio process tap + aggregate device**로 한다

```text
Status:   PROVISIONAL — measured on one machine, not yet implemented
Date:     2026-09-08
Phase:    (아직 Phase가 아니다 — 운영자 결정 대기)
Scope:    macOS에서 마이크와 시스템 오디오를 함께 녹음하는 경로의 후보 비교 ·
          spike 실측 · AirPods 처리 · 아직 재지 않은 것
```

Status가 `PROVISIONAL`인 이유는 §2에 있다. **구현되지 않았고, 스펙에도 없다.**

---

## 1. Context

지금 이 앱은 **마이크 하나만** 녹음한다 (ADR-0003 · `cpal` + `hound`). 운영자가
2026-09-08에 온라인 회의(Google Meet · Zoom)로 확장하기를 요청했다.

```text
내 목소리      맥 마이크
상대 목소리    macOS 시스템 오디오
```

**오디오만 저장하면 된다.** 화면도 영상도 필요 없다.

---

## 2. 이 문서의 상태 — 왜 `Accepted`가 아닌가

세 가지가 아직 없다.

```text
구현        한 줄도 쓰지 않았다. 아래 근거는 전부 저장소 밖 spike에서 나왔다
스펙        PRODUCT-SPEC은 마이크 녹음만 말한다. 시스템 오디오는 §15 Non-Goal에도
            §16 Deferred에도 없다 — **적힌 적이 없다.** 운영자 결정이 먼저다
검증        §7의 네 항목이 재지 않은 채 남아 있다
```

"녹음 앱 하나 쓰려고 시스템 드라이버를 넣어야 하는" 제품이 된다. **탈락.**

## 5. 선택 — 4.1 (Core Audio process tap)

**권한이 결정했다.**

이 앱은 §12에서 *"오디오는 기기 밖으로 나가지 않는다"* 를 약속한다. 그 앱이 사용자에게
**"화면 및 시스템 오디오 녹화"** 를 허용해 달라고 하는 것은, 하는 일과 묻는 것이 어긋나는
일이다. 오디오만 필요하면 오디오 권한만 물어야 한다.

부수적으로 4.1이 더 가볍다 — 영상 파이프라인이 없고, 프레임 전달 경로도 없다.

⚠️ **4.1에는 함정이 하나 있다** [D]. API는 public인데 **그 권한을 요청하거나 가지고
있는지 확인하는 public API가 없다.** 공개 샘플(AudioCap)은 private TCC 메서드를 쓰며,
그것을 끄는 빌드 플래그를 따로 두고 있다. 앱스토어 배포를 하게 되면 이 항목이 다시 열린다.

## 6. spike가 실제로 잰 것 (2026-09-08)

저장소 밖에서 Swift로 재었다. **제품 코드는 한 줄도 바뀌지 않았다.**

### 6.1 tap과 aggregate device는 만들어진다 [A✓]

```text
AudioHardwareCreateProcessTap          status = 0
AudioHardwareCreateAggregateDevice     status = 0
aggregate 입력                          3채널 · 스트림 2개 · 48 kHz · Float32
```

3채널의 정체는 **마이크 1 + tap 2(스테레오)** 다.

### 6.2 마이크와 시스템 오디오가 **함께** 온다 [A✓]

시스템 사운드를 재생하면서 6초를 쟀다.

```text
채널 0   -46.2 dBFS   마이크
채널 1   -33.4 dBFS   시스템 오디오 L
채널 2   -35.0 dBFS   시스템 오디오 R
```

**같은 `AudioDeviceIOProc`, 같은 클럭으로 온다.** 두 스트림을 따로 열어 나중에 맞출 때
생기는 드리프트가 이 구조에는 없다 — 그것이 aggregate device를 쓰는 이유다.

### 6.3 ⚠️ `isExclusive`가 없으면 무음만 나온다 [A✓]

```swift
CATapDescription(stereoMixdownOfProcesses: [])   // 빈 목록
tapDesc.isExclusive = true                        // ← 이것이 있어야 "전부"가 된다
```

**빈 목록만으로는 "아무 프로세스도 아님"이다.** `isExclusive`를 켜야 그 목록이 *제외*
목록으로 읽혀 전부를 잡는다. 이것을 모르면 tap이 성공(status 0)하고도 계속 무음이 나오며,
실패가 아니라서 원인을 찾기 어렵다. **2026-09-08에 실제로 이 함정에 빠졌다.**

### 6.4 ❌ `cpal`로는 이 장치를 읽을 수 없다 [A✓]

이것이 이 문서에서 가장 중요한 측정이다.

```text
cpal이 aggregate device를 목록에서 보는가     ✅ 이름이 뜬다
cpal이 3채널을 줄 수 있는가                   ❌ 지원 config가 전부 channels: 1
IsStacked: true 로 한 스트림으로 합치면        ❌ cpal 목록에서 아예 사라진다
```

**`cpal`로 열면 마이크만 오고 tap 채널은 오지 않는다.** 그래서 회의 녹음은 기존 캡처
경로를 재사용할 수 없고, `AudioDeviceIOProc`을 직접 써야 한다 — spike가 그쪽은 된다는
것을 6.2에서 보였다.

**[U]** cpal이 왜 첫 스트림만 보는지는 확인하지 않았다. 그 원인을 고치면 재사용할 수
있을지도 모르지만, 그것을 알아보는 비용과 직접 쓰는 비용을 비교한 적이 없다.

## 7. 아직 재지 않은 것 [U]

**넷 다 코드나 장비 없이는 답이 나오지 않는다.**

| | 왜 중요한가 |
| --- | --- |
| **AirPods를 끼면 tap이 몇 Hz를 받는가** | 마이크를 쓰면 A2DP → HFP로 떨어진다 [D]. HFP에는 16 kHz(mSBC)와 8 kHz(CVSD)가 있고, **8 kHz면 전사 품질이 실제로 떨어진다.** 16 kHz면 whisper의 기본 입력과 같아 잃는 것이 거의 없다 |
| **Zoom/Meet가 마이크를 잡고 있을 때 우리도 열 수 있는가** | 못 열면 회의 중에 녹음이 시작되지 않는다 — 정확히 필요한 순간에 |
| **번들된 앱에서 권한이 어떻게 뜨는가** | spike는 터미널에서 돌았고 **부모 프로세스의 권한을 물려받았을 수 있다.** 실제 앱에서는 다를 수 있다 |
| **tap 중에 소리가 계속 들리는가** | `muteBehavior = .unmuted`로 두었으나 **귀로 확인하지 않았다.** 회의 중에 상대 목소리가 안 들리면 그것은 녹음이 아니라 사고다 |

**첫째를 재는 도구는 만들어 두었다** (`airpods.swift` — 기본 입력 장치를 그대로 쓰므로
AirPods를 끼면 자동으로 그것을 잡는다). 2026-09-08에는 운영자가 회사에 있어 AirPods를
연결할 수 없었다.

---

## 8. AirPods를 어떻게 다룰 것인가

운영자가 명시했다 (2026-09-08): **"에어팟 끼면 바로 인식돼서 말하고 듣는 것 전부 가능"**.

**HFP 전환은 피할 수 없다** [D] — Bluetooth 규격이지 macOS의 결함이 아니다. 마이크를
쓰는 순간 출력까지 함께 내려간다.

**그러나 이 앱에는 손해가 작을 가능성이 높다** [U].

```text
whisper가 받는 것    16 kHz mono
HFP(mSBC)가 주는 것   16 kHz mono
```

음악을 들을 때는 HFP가 나쁘지만, 이 앱의 목적은 **말을 글로 옮기는 것**이다. §7의 첫
항목이 8 kHz로 나오지 않는 한, 잃는 것은 음질이지 전사 품질이 아니다.

**자동 인식은 어렵지 않다** [D]. 기본 입력 장치가 바뀌는 것을
`kAudioHardwarePropertyDefaultInputDevice` 리스너가 알려주고, aggregate device를 그
장치로 다시 만들면 된다.

**막지 않고 알린다.** 오늘 만든 입력 레벨 표시와 같은 태도다 (ADR-0003 §16.5) — 8 kHz로
떨어지는 것이 확인되면 그 사실을 화면이 말하되, 녹음을 멈추지도 막지도 않는다.

## 9. 회의 모드를 나눈다 (운영자 결정 · 2026-09-08)

처음에는 **모드를 나누지 않는 쪽**을 검토했다 — 모드를 나누면 사람이 회의 시작 전에
켜는 것을 잊고, 그렇게 잃은 상대 목소리는 되돌릴 수 없기 때문이다.

**운영자가 나눠도 된다고 결정했다.** 그 결정이 구조를 단순하게 만든다.

```text
평소 녹음    지금 그대로 (cpal · 마이크)          ← 손대지 않는다
회의 모드    Core Audio · aggregate(마이크 + tap)  ← 새 경로
```

**기존 녹음 경로를 건드리지 않는 것**이 이 선택의 가장 큰 값이다. 녹음은 이 앱에서 가장
되돌릴 수 없는 부분이고, 2026-09-08에 2시간짜리 녹음을 거의 잃을 뻔한 사고가 있었다.

⚠️ **대가는 녹음 코드가 두 벌이 된다는 것이다.** 사고가 났을 때 어느 경로인지부터
갈라야 한다. 그 대가를 줄이려면 두 경로가 **같은 파일 쓰기와 같은 종료 규칙**을 공유해야
한다 (`WavFile::finish` · ADR-0003 §5.5).

## 10. 저장 형태 — 아직 정하지 않았다

두 갈래가 있고, 이 문서는 고르지 않는다.

```text
(가) mono로 섞어 저장          지금 파이프라인 그대로. 누가 말했는지는 사라진다
(나) 스테레오로 저장            L = 내 마이크 · R = 시스템
                              → 채널을 따로 전사하면 **[나] / [상대] 가 공짜로 나온다**
```

**(나)는 화자 분리를 별도 기술 없이 2인까지 준다.** 화자 분리는 PRODUCT-SPEC §15의
Non-Goal이지만, 이것은 화자를 *분리하는* 기술이 아니라 애초에 **따로 들어온 두 소리를
따로 두는 것**이다. 그럼에도 결과가 Non-Goal과 같아 보이므로 **운영자 결정이 필요하다.**

⚠️ (나)를 고르면 `transcription/audio_input.rs`가 mono로 접는 규칙(ADR-0007 §9)을
다시 봐야 한다.

## 11. 이 문서가 하지 않는 것

- **Windows를 정하지 않는다.** 위 전부가 macOS API다. Phase 6이 Windows를 볼 때 이
  기능이 어떻게 되는지는 여기서 답하지 않는다.
- **구현 Phase를 만들지 않는다.** PRODUCT-SPEC에 이 기능이 적힌 뒤의 일이다.
- **ADR-0003을 다시 열지 않는다.** 평소 녹음의 engine 선택은 그대로다.
- **§7의 네 항목을 추정으로 채우지 않는다.**
