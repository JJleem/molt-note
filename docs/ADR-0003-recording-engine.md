# ADR-0003 — recording engine은 **잠정적으로** Rust/native 경로(`cpal` + `hound`)로 한다

```text
Status:   PROVISIONAL — pending human device validation
Date:     2026-09-02
Phase:    Phase 2A — Recording Engine Validation
Task:     TASK-010 (작성) · TASK-011 · TASK-012 · TASK-013 (자동 검증 근거) · TASK-014 (실행 절차 · 기록표)
Scope:    recording engine 후보 비교 · 잠정 선택 · 근거의 종류 구분 · 사람이 확인해야 할 것과 그 확인 절차
```

Status가 `PROVISIONAL`인 이유는 §2에 있다. 확정되려면 무엇이 필요한지는 §12,
그것을 사람이 어떻게 확인하는지는 §12.1이다.
**§12의 8개 항목은 하나도 확인되지 않았다** (§4.2.4).

> **2026-09-02 — 장치 검증이 Final Integration으로 연기됐다.** 자세한 것은 §12의 머리말과
> §12.A(ASSUMPTION A-REC-001)에 있다. 이 문서는 **PROVISIONAL로 남는다** —
> 실제 장치 증거가 생기기 전까지 `CONFIRMED` · `ACCEPTED` · `VERIFIED ON DEVICE`로 바꾸지 않는다.

---

## 1. Context

`docs/PRODUCT-SPEC.md` §6.1은 recording engine 선택을 **결정해야 할 아키텍처 선택(CANDIDATE)** 으로
남겨 두고, 14개 기준 전체를 ADR에 기록하라고 요구한다. 같은 절은 이 결정을 **두 단계로** 내리라고
못박는다 — 결정을 좌우하는 사실 중 일부(실제 권한 프롬프트 · 실제 컨테이너/코덱 · 실제 음질)는
**자동으로 확인할 수 없고 사람이 앱을 실행해야만** 알 수 있기 때문이다.

```text
Phase 2A  후보 비교 → 잠정 선택 → 최소 spike        (자동 검증 + 저장소 근거)
    ↓
Human Review  실제 장치에서 짧은 smoke recording     (사람만 알 수 있는 것)
    ↓
확정          ADR-0003이 확정 상태가 된다
    ↓
Phase 2B  production recording 구현
```

이 문서는 그 흐름의 **첫 칸**이다. 후보를 비교하고 잠정 선택을 적되,
**사람의 장치 검증이 아직 없으므로 확정하지 않는다.**

`phase-prompt/02a-recording-engine-validation.md`가 이 단계의 Goal이다.

## 2. 이 문서의 상태 — 왜 `Accepted`가 아닌가

ADR-0001과 ADR-0002는 `Status: Accepted`다. 이 문서는 아니다.

두 문서가 확정될 수 있었던 이유는 그 결정의 근거가 **저장소 안에서 끝났기** 때문이다 —
`rusqlite`의 `bundled` feature는 로컬 빌드 산출물로 확인됐고(ADR-0001 §4),
`NSMicrophoneUsageDescription`의 위치는 파일 검사로 판정된다(ADR-0002 §5.1).

recording engine은 다르다. **이 결정을 뒤집을 수 있는 사실이 저장소 밖에 있다.**
실제 마이크가 열리는지, TCC 프롬프트가 뜨는지, 만들어진 파일이 실제로 들리는지는
사람이 번들된 앱을 실행해야만 알 수 있다 (§12).

> **이 문서를 "결정됐다"로 인용하지 않는다.** §12의 8개 항목이 모두 확인되기 전까지
> 이 선택은 되돌릴 수 있는 상태로 유지된다. Phase 2B는 이 문서가 확정된 뒤에 시작한다.

## 3. 근거의 세 종류 — 이 문서의 표기 규칙

`docs/PRODUCT-SPEC.md` §18은 자동으로 판정할 수 없는 것을 자동 PASS로 적지 말라고 요구한다.
이 문서의 모든 주장에는 **어떻게 알게 됐는지**를 나타내는 태그가 붙는다.

| 태그 | 뜻 |
| --- | --- |
| **[R]** | **저장소 근거** — `docs/PRODUCT-SPEC.md` §14에 이미 조사되어 있는 사실. **이 Task는 재조사하지 않고 인용한다.** 인용한 절을 함께 적는다. |
| **[A✓]** | **자동 검증 — 확인됨.** 이 Task에서 저장소 파일을 직접 읽어 확인했다. 근거 파일 경로를 함께 적는다. |
| **[A?]** | **자동 검증 가능 — 아직 하지 않음.** 이 저장소의 컴파일·테스트로 판정할 수 있으나, 이 Task는 문서만 쓰므로 실행하지 않았다. **후속 Task의 Gate가 판정한다.** |
| **[H]** | **Human Review** — 실행 중인 앱과 실제 하드웨어가 있어야만 알 수 있다. 자동으로 판정할 수단이 없다. |
| **[U]** | **UNVERIFIED** — 확인되지 않았고 이 Task에 확인할 수단도 없다. §14.3이 UNVERIFIED로 남긴 것은 **여기서도 UNVERIFIED다.** |

두 태그가 겹치는 경우가 있다. 예를 들어 **[R][U]** 는 "§14.3이 조사했고, 그 결과가
'아직 확인되지 않았다'였다"는 뜻이다. 그런 항목을 이 문서가 승격시키지 않는다.

> **이 Task는 Gate를 실행하지 않았다.** `.loop/tasks/TASK-010.yaml`의 `stop_condition.gates`가
> 비어 있고 문서만 바꾸기 때문이다. 따라서 **[A✓]** 는 "파일을 읽어 확인했다"는 뜻이지
> "build/lint/test가 통과했다"는 뜻이 아니다. 이 구분을 흐리지 않는다.

## 4. 후보

§6.1은 최소 둘(webview · native)을 요구하고, §14.3은 세 번째(커뮤니티 플러그인)를 함께 조사해 뒀다.
셋 모두를 비교 대상으로 둔다.

| | 후보 | 요약 |
| --- | --- | --- |
| **A** | **WebView / MediaRecorder** | 프론트엔드가 `getUserMedia` + `MediaRecorder`로 캡처하고, 결과 blob을 Rust 쪽에 넘겨 파일로 만든다 |
| **B** | **Rust/native 오디오 경로 (`cpal` + `hound`)** | Rust backend가 입력 장치를 열어 PCM 콜백을 받고, WAV writer로 직접 파일을 만든다 |
| **C** | **커뮤니티 Tauri 플러그인** | `tauri-plugin-audio-recorder`(brenogonzaga) · `tauri-plugin-mic-recorder`(ayangweb) |

**후보 C에 대해 §14.3이 확인해 둔 사실 하나가 비교의 성격을 바꾼다** — [R §14.3]
**공식 Tauri 오디오 녹음 플러그인은 없고, 커뮤니티 플러그인 2개는 모두 내부적으로 `cpal` + `hound`를 쓴다.**
즉 C는 B의 대안이 아니라 **B를 감싼 포장**이다. C의 평가는 "다른 오디오 경로인가"가 아니라
"이 포장을 신뢰할 수 있는가"의 문제가 된다 (§7.2).

### 4.1 현재 저장소 상태 — 아직 아무 후보도 설치되어 있지 않다 [A✓]

| 사실 | 근거 |
| --- | --- |
| `src-tauri/Cargo.toml`의 의존성은 `tauri` · `serde` · `serde_json` · `rusqlite`뿐이다. **`cpal`도 `hound`도 없다.** | `src-tauri/Cargo.toml` |
| `package.json`에 오디오 관련 의존성이 없다 | `package.json` |
| 오디오 캡처 코드가 없다 — `src-tauri/src` 아래는 `commands` · `db` · `domain` · `platform`뿐이다 | 소스 트리 |
| `NSMicrophoneUsageDescription` 선언은 이미 있다 (ADR-0002) | `src-tauri/Info.plist` · `tests/macos-bundle.test.ts` |
| 이 프로젝트의 Gate는 `build` · `lint` · `test` 셋이다. `tauri build`는 Gate가 아니다 | `.loop/project.yaml` |

> **따라서 이 문서의 어떤 문장도 "cpal이 이 기기에서 동작한다"를 주장하지 않는다.**
> 그것을 주장하려면 최소한 의존성이 해석되고 컴파일돼야 하며, 그것조차 "장치가 열린다"와는 다른 말이다.

### 4.2 자동 검증 — 이 저장소가 실제로 증명한 것 (2026-09-02 · TASK-011 · 012 · 013)

§4.1은 TASK-010 시점의 사실이었다. 그 뒤 세 Task가 잠정 선택된 경로를 실제로 만들었다 —
**입력 장치 열거**(TASK-011) · **캡처와 파일 확정**(TASK-012) · **사람이 누를 수 있는 임시
표면**(TASK-013).

**이 절이 적는 것은 세 가지뿐이다** — 해석된 의존성 버전 · 자동 테스트가 덮는 순수 로직 ·
**코드가 만들도록 되어 있는 포맷.** 마지막 것은 "만들어진 파일이 그 포맷이더라"가 아니다.
이 저장소는 장치를 연 적이 없으므로 그것을 알지 못한다 (§12).

#### 4.2.1 해석된 의존성 [A✓]

추측한 값이 아니라 **의존성 해석과 Gate 빌드가 만든 값**이다.

| 사실 | 근거 파일 |
| --- | --- |
| `src-tauri/Cargo.toml`이 `cpal = "0.18"`을 요구한다 | `src-tauri/Cargo.toml` |
| 실제로 해석된 버전은 **`cpal` 0.18.2**이며, §14.3이 조사한 값과 같다 | `src-tauri/Cargo.lock` (`name = "cpal"` / `version = "0.18.2"`) |
| `src-tauri/Cargo.toml`이 `hound = "3"`을 요구한다 — **TASK-012가 추가했다** | `src-tauri/Cargo.toml` |
| 실제로 해석된 버전은 **`hound` 3.5.1**이며, §14.3이 조사한 값과 같다. §9가 dormant로 적은 것이 바로 이 버전이다 | `src-tauri/Cargo.lock` (`name = "hound"` / `version = "3.5.1"`) |
| 이 조합이 이 기기에서 **컴파일된다** — `build` · `lint`(clippy `-D warnings`) · `test` Gate가 전부 green이다 | `.loop/evidence/TASK-011/` · `.loop/evidence/TASK-012/` · `.loop/evidence/TASK-013/` |

`cpal` 0.18.2의 API 중 이 저장소가 **실제로 컴파일해 확인한 것**만 적는다 [A✓].

```text
cpal::default_host()                       → Host
HostTrait::default_input_device()          → Option<Device>
HostTrait::input_devices()                 → Result<_, cpal::Error>  (Device의 iterator)
DeviceTrait::description()                 → Result<DeviceDescription, cpal::Error>
DeviceDescription::name()                  → &str
DeviceTrait::default_input_config()        → 장치가 알려주는 기본 형식
DeviceTrait::build_input_stream(...)       → Stream  (I16 · F32 샘플 형식 두 경로)
StreamTrait::play()
```

> **여기까지가 컴파일이 증명하는 전부다.** 이 호출들이 실제로 장치를 돌려주는지, 스트림이
> 실제로 열리는지, macOS TCC 프롬프트를 유발하는지, 열거된 이름이 사람이 아는 마이크 이름과
> 같은지는 **여전히 [H]다** (§12).
> `DeviceTrait::id()`가 돌려주는 `DeviceId`도 있으나, 그 값이 앱 실행 사이에서 안정적인지는
> 확인하지 않았으므로 선택 키로 쓰지 않았다 [U].

#### 4.2.2 자동 테스트가 덮는 순수 로직 [A✓]

실제 하드웨어를 부르는 코드는 `src-tauri/src/audio/system_devices.rs`와
`src-tauri/src/audio/system_capture.rs` **두 파일 안에만** 있다. 그 바깥은 경계 뒤에 대체
구현을 넣으면 제품 코드가 그대로 지나가므로, 아래는 **마이크도 마이크 권한도 없이 판정된다**
(§18 · §5.13).

| 덮이는 것 | 어디서 |
| --- | --- |
| 장치 목록 정규화 — 빈 목록(정상 상태) · 중복 이름 · 이름 없는 장치 · 선택 키의 안정성 · 기본 장치 표시 · 정렬 | `src-tauri/src/audio/devices.rs` · `src-tauri/tests/input_devices.rs` |
| 출력 경로 결정 — 같은 입력이면 같은 값 · **이미 있는 파일을 덮어쓰지 않음** · 이름 규칙 | `src-tauri/src/audio/capture.rs` |
| 포맷 기술 문장 — 샘플레이트 · 채널 수 · 비트 심도 · 컨테이너 네 값이 모두 들어간다 | `src-tauri/src/audio/capture.rs` |
| **파일 확정 경로 전체** — 가짜 샘플 소스로 start → stop을 지나 WAV writer가 파일을 확정하고, 크기를 **파일시스템에서 읽어** 보고한다 | `src-tauri/tests/capture.rs` |
| 실패 계약 — 장치를 열지 못함 · 캡처 중단(그때까지의 파일은 남는다) · 녹음 자리를 만들지 못함이 `Failure`로 도달하고 `audioDevice`로 직렬화된다 | `src-tauri/tests/capture.rs` · `tests/ipc-boundary.test.ts` |
| spike 표면의 상태 — 빈 목록 · `idle → recording → finished` · 결과 표시 · 실패 | `src/screens/captureSpikeView.test.ts` |
| `NSMicrophoneUsageDescription`이 `src-tauri/Info.plist`에 있고 `tauri.conf.json`에 없다 | `tests/macos-bundle.test.ts` (ADR-0002 §5.1) |

> **가짜 샘플 소스가 만든 파일은 그 테스트가 만든 샘플로 된 파일이다.** 실제 마이크가 그
> 자리에 있었다는 뜻이 아니고, 그 파일이 사람이 알아들을 수 있는 소리라는 뜻도 아니다.

#### 4.2.3 코드가 만들도록 되어 있는 포맷 [A✓ — 코드에 대해서만]

| 코드가 고정하는 것 | 코드가 고정하지 않는 것 |
| --- | --- |
| 컨테이너는 **WAV(RIFF)**, 샘플은 **16-bit 정수 PCM**이다 (`hound::SampleFormat::Int` · `bits_per_sample = 16`) | **샘플레이트와 채널 수** — `default_input_config()`가 알려준 값을 그대로 쓴다 |
| 장치가 `f32`를 주면 16-bit로 옮기며, 범위를 벗어난 값은 반대 부호로 감기지 않고 잘린다 | **리샘플링도 다운믹스도 없다.** 16kHz mono로 맞추는 코드가 이 저장소에 없다 |

**그래서 §14.4의 whisper 입력 요구와의 대조는 절반만 코드로 답이 나온다.**
`16-bit WAV`는 코드가 고정하지만, 모델이 기준으로 삼는 `16kHz mono`는 **장치가 정한다.**
이 기기의 장치가 무엇을 주는지 이 저장소는 알지 못한다 — §12의 항목 7이 그것을 판정한다.

#### 4.2.4 이 저장소가 실행하지 않은 것

- **`npm run tauri build`를 실행한 적이 없다 — 번들을 만든 적이 없다.** `tauri build`는 이
  프로젝트의 Gate가 아니다 (`.loop/project.yaml`의 Gate는 `build` · `lint` · `test` 셋뿐이고
  `npm run build`는 프론트엔드 빌드다). ADR-0002 §5.2가 이미 같은 이유로 번들 `Info.plist`
  병합을 UNVERIFIED로 남겼다.
- **앱을 실행한 적이 없다.** 장치를 연 적도, 권한 프롬프트를 본 적도, 만들어진 파일을 들어
  본 적도 없다.
- 따라서 **§12는 하나도 채워지지 않았고, 이 문서의 상태는 여전히 `PROVISIONAL`이다.**

## 5. §6.1 평가 기준 전체 비교

§6.1이 나열한 14개 기준이다. **하나도 생략하지 않는다.**

```text
recording reliability      microphone enumeration     microphone selection
pause/resume               file finalization          data-loss behavior
audio format               transcription compatibility
macOS permission behavior  Windows compatibility
Tauri integration          packaging
testability                maintenance cost
```

### 5.1 recording reliability

| 후보 | 관찰 | 태그 |
| --- | --- | --- |
| A | WKWebView에서 `getUserMedia`/`MediaRecorder`는 **원리상** 동작한다. 다만 Tauri #5853 — `getUserMedia`가 앱을 멈추게 한다는 보고가 있다 | [R §14.3] |
| A | 1시간 규모 녹음에서의 안정성과 crash 내성(R-005) | [R §14.3][U] — §14.3이 "Phase 2에서 반드시 실제 확인할 것"으로 남긴 항목 |
| B | `cpal` macOS 백엔드는 CoreAudio이며 입력 캡처를 지원한다 | [R §14.3] |
| B | 캡처가 webview lifecycle과 분리된다 → R-001("녹음 중 UI state가 변경되더라도 session이 쉽게 유실되지 않는다")에 유리하다는 **추론**이다. 실제 유실 내성은 측정하지 않았다 | [U] |
| C | 내부가 B와 같으므로 신뢰성의 상한은 B와 같고, 그 위에 플러그인 자체의 결함 가능성이 더해진다 | [R §14.3] + 추론 |

**판단**: 세 후보 모두 **장시간 신뢰성은 확인되지 않았다.** 이 기준은 어느 쪽도 이기지 못한다.
§6.1이 "결정적"이라고 지목한 셋 중 `data-loss behavior`(5.6)만 이 단계에서 부분적으로 논할 수 있다.

### 5.2 microphone enumeration

## 6. 잠정 선택

> **후보 B — Rust/native 오디오 경로(`cpal` + `hound`)를 잠정 선택한다.**
> 이것은 **결정이 아니라 검증 대상**이다. §12가 이 선택을 지지하거나 반박한다.

선택을 지지하는 근거를 **강한 순서로** 적는다. 각 근거의 태그가 곧 그 근거의 강도다.

### 6.1 이 선택이 뒤집히는 조건

잠정 선택은 **반증 조건을 함께 적을 때만** 잠정적이다. 다음 중 하나라도 사실이면
Phase 2B를 시작하지 않고 이 문서를 다시 연다.

```text
· 이 기기에서 cpal이 입력 장치를 열지 못한다                        (§12 항목 3)
· 번들된 .app에서 마이크 TCC 프롬프트가 뜨지 않는다                  (§12 항목 1)
· 만들어진 파일이 재생되지 않거나 알아들을 수 없다                    (§12 항목 5·6)
· 출력이 16-bit PCM WAV가 아니어서 근거 1이 성립하지 않는다          (§12 항목 7)
· Stop이 손상된 파일을 남긴다                                       (§12 항목 8)
```

반대 방향의 반증도 적어 둔다 — **후보 A가 macOS와 Windows 양쪽에서 16-bit PCM WAV를
동일하게 낸다는 사실이 확인되면, 근거 1과 2가 동시에 사라지고 이 결정은 재검토되어야 한다.**

## 8. 평가의 비대칭 — 이 결정의 가장 약한 지점

§6.1이 직접 경고한 항목이며, **이 문서에서 가장 중요한 절이다.**

> 평가의 비대칭에 주의한다: native 경로의 핵심 근거는 자동 검증 가능하고 webview 경로의
> 핵심 미지수는 그렇지 않다. **"검증하기 쉬운 쪽"이 그 이유만으로 선택되면 근거가 아니라 편향이다.**

이 비대칭은 실재한다. §5의 태그 분포가 그것을 그대로 보여 준다.

```text
후보 B의 핵심 근거      →  [R] 저장소 근거 · [A✓] 파일 확인 · [A?] 컴파일로 확인 가능
후보 A의 핵심 미지수    →  [H] 사람이 앱을 실행해야 함 · [U] 확인되지 않음
```

이 상태에서 "B는 근거가 많고 A는 미지수가 많다"고 세어서 B를 고르면, 실제로 측정한 것은
**두 후보의 품질이 아니라 이 저장소의 검증 수단이 어디까지 닿는가**이다. 그것은 근거가 아니다.

그래서 §6의 근거 목록은 이렇게 만들어졌다.

| | 내용 |
| --- | --- |
| **근거로 쓴 것** | 근거 1·2·3 — 전부 **후보의 성질**에 대한 진술이다. 근거 1과 2는 §14.3·§14.4의 **저장소 근거 대조**에서 나오며, 검증 용이성과 무관하게 성립한다 |
| **근거로 쓰지 않은 것** | 근거 5(testability) — 이것은 **후보의 성질이 아니라 우리 도구의 성질**이다. §5.13에서 B에 유리하다고 적었지만, §6의 선택 근거로는 세지 않았다 |
| **불리한 근거로 쓰지 않은 것** | 후보 A의 [U] 항목 전부 — §7.1이 그것을 탈락 사유에서 분리해 둔 이유가 이것이다 |

**남는 위험을 그대로 적는다.** 근거 1·2가 §14.3 인용에 의존하고 있고, 이 Task는 그것을
재조사하지 않았다(재조사하지 말라는 것이 Phase Goal의 지시다). 즉 **이 결정의 가장 단단한 축조차
2026-09-01의 조사 결과를 신뢰하는 데서 출발한다.** §12의 항목 7이 그 축을 실제 파일로
확인하는 자리이며, 그래서 그 항목은 §12의 기록표에서 뺄 수 없다.

**그리고 후보 A의 미지수는 여전히 미지수로 남는다.** Phase 2A는 B의 spike만 만들므로,
이 단계가 끝나도 A에 대해 새로 알게 되는 것은 없다. 이것은 의도된 절충이며(§6.1의 2단계 구조),
**A가 반증됐다는 뜻이 아니다.** 근거 1·2가 흔들리면 A는 조사되지 않은 채 남아 있는
후보로서 다시 검토 대상이 된다.

## 10. Windows 함의

**이 Phase는 Windows 빌드·실행·권한 로직을 만들지 않는다** (Phase 6). 아래는 §3.1과 §14.3에 따라
**평가 근거로만** 적는 것이며, 구현 계획이 아니다.

1. **§3.1은 Windows를 지원 대상 플랫폼으로 두고, core/domain이 특정 OS에 의존하지 않을 것을
   요구한다(INV-10).** engine 선택은 이 요구를 정면으로 건드린다 — 캡처는 §3.1이 지목한
   `RecordingBackend` 경계 자리이기 때문이다.
2. **후보 B는 같은 crate가 CoreAudio(macOS)와 WASAPI(Windows)를 덮으며 같은 출력 포맷을 낸다**
   [R §14.3]. 즉 플랫폼 분기가 `cpal` 안에 있고 이 프로젝트의 domain에는 없다.
3. **후보 A는 플랫폼마다 다른 webview 엔진에서 다른 코덱을 낼 수 있다** [R §14.3].
   그러면 포맷 차이가 domain 위쪽(전사 입력 준비)으로 새어 나온다.
4. **macOS 검증 결과의 이전 가능성이 다르다.** §12를 macOS에서 통과해도,
   후보 A였다면 그 결과가 Windows에 대해 말해 주는 것이 거의 없다. B는 최소한
   "같은 crate·같은 포맷"이라는 저장소 근거를 남긴다 — 그것도 **실측이 아니라 근거일 뿐이다.**
5. **Windows 권한**: 일반 Win32 앱에는 manifest 선언이 불필요하다
   [R §14.3 · VERIFIED-by-secondary-corroboration — §14.3의 표기를 그대로 유지한다].
   단 Settings의 "Let desktop apps access your microphone" 토글이 OS 수준에서 차단할 수 있고,
   **차단 시 앱이 받는 정확한 오류는 UNVERIFIED다** [R §14.3][U]. Phase 6이 실측한다.
6. **`msi` 번들은 Windows 머신 없이 만들 수 없다** [R §14.2]. engine 선택과 독립적인 제약이며
   Phase 6의 packaging 계획에 속한다.

### 12.0 각 항목의 뜻과 실패했을 때의 의미

1. **macOS 마이크 권한 프롬프트가 실제로 뜨는가** — `NSMicrophoneUsageDescription` 문구가
   프롬프트에 보이는지 함께 본다. 프롬프트가 **언제** 떴는지도 적는다 (§12.1의 5단계).
   실패 시: ADR-0002의 packaging 전제 또는 §5.9의 TCC 동작 가정이 무너진다.
2. **선택한 물리 마이크가 실제로 사용되는가** — 고른 장치에만 대고 말한 소리가 결과 파일에
   들어 있는지로 판단한다. 화면의 `Device` 값은 **고른 이름이 아니라 열린 장치가 알려준
   이름**이므로 그것도 함께 본다. 실패 시: 장치 열거/선택의 대응이 깨진 것이다 (§5.2 · §5.3).
3. **장치가 정상적으로 열리는가** — 오류 없이 상태가 `Recording…`이 되는가.
   실패 시: §6.1의 첫 번째 반증 조건이다.
4. **10~20초 녹음이 성공하는가** — 중간에 멈추거나 앱이 죽지 않는가. 정지할 때
   "일부 구간이 유실됐다"나 "중간에 끊겼다"가 보이면 그것도 이 항목의 관찰이다.
5. **출력 파일이 실제로 존재하는가** — 보고된 경로에 파일이 있고 크기가 0이 아닌가 (R-002).
6. **녹음된 음성이 알아들을 수 있는가** — 재생해서 사람이 듣는다. 무음·잡음·과도한 클리핑이
   아닌지. **이 항목은 어떤 자동 검사로도 대체되지 않는다.**
7. **실제 컨테이너 / 코덱 / PCM 포맷이 기대와 일치하는가** — §14.4의 whisper 입력
   요구(16-bit WAV · 모델은 16kHz mono 기준)와 대조한다. **§6의 근거 1이 이 항목에 걸려 있다.**
   네 값(컨테이너 · 비트 심도 · 샘플레이트 · 채널)을 각각 적는다 — 앞의 둘은 코드가 고정하고
   뒤의 둘은 장치가 정하므로, 어긋난다면 **어느 쪽이** 어긋났는지가 곧 결론을 가른다 (§4.2.3).
8. **Stop / 확정이 손상된 파일 없이 끝나는가** — 정지 직후의 파일이 그대로 재생 가능한가
   (§5.5 · R-002).

### 12.1 실행 방법 — 정확한 명령과 조작 순서

> **이 절차는 이 저장소의 `package.json` 스크립트 · `tauri.conf.json` · 실제 소스 구조에서
> 그대로 나온 것이다. 그러나 이 절을 쓴 Task는 번들을 만들지도 앱을 실행하지도 않았다**
> (§4.2.4). **아래는 관찰 기록이 아니라 사람이 따라갈 절차다.** 실제로 무엇이 일어나는지를
> 받는 자리는 §12의 표다.

#### 0단계 — 전제

| | |
| --- | --- |
| 기기 | macOS. **실제 마이크가 있어야 한다** (내장 마이크로 충분하다) |
| 툴체인 | Node · npm · Rust. `cpal`의 MSRV가 **1.85 이상**을 요구한다 [R §14.3]. §14.1 기준 이 기기는 rustc 1.94.0이다 |
| Xcode | desktop 전용이므로 **Command Line Tools로 충분하다** [R §14.2] |
| 의존성 | `node_modules`가 없다면 먼저 `npm install` |
| 시간 | 첫 릴리스 빌드는 Rust 의존성 전체를 컴파일하므로 오래 걸린다. **녹음 자체는 10~20초다** |

명령은 전부 **저장소 루트**에서 실행한다.

#### 1단계 — 번들된 `.app`을 만든다

```bash
npm run tauri build
```

`package.json`의 `"tauri": "tauri"` 스크립트를 지나 Tauri CLI가 실행된다.
`tauri.conf.json`의 `beforeBuildCommand`가 `npm run build`(= `tsc && vite build`)를 먼저 돌리므로
프론트엔드를 따로 빌드할 필요는 없다.

산출물을 확인한다. `Molt Note`는 `tauri.conf.json`의 `productName`이다.

```bash
ls -d "src-tauri/target/release/bundle/macos/Molt Note.app"
```

이 경로에 없으면 실제 위치를 찾는다:

```bash
find src-tauri/target/release/bundle -maxdepth 2 -name "*.app"
```

> `tauri.conf.json`의 `bundle.targets`가 `"all"`이므로 `.app` 외의 산출물도 함께 만들어진다.
> **이 절차가 쓰는 것은 `.app` 하나뿐이다.** 뒤쪽 번들 단계에서 빌드가 실패하더라도 `.app`이
> 이미 만들어져 있다면 그것으로 진행할 수 있다.

#### 2단계 (선택) — `Info.plist` 병합을 미리 확인한다

항목 1은 프롬프트에 **문구가 보이는지**까지 본다. 그 문구가 번들에 들어갔는지는 앱을
실행하기 전에 확인할 수 있다 — ADR-0002 §5.2가 남긴 명령이 그대로 쓰인다.

```bash
plutil -p "src-tauri/target/release/bundle/macos/Molt Note.app/Contents/Info.plist" \
  | grep NSMicrophoneUsageDescription
```

여기서 문구가 보이지 않으면, 항목 1의 실패 원인은 캡처 경로가 아니라 **packaging 전제**다
(ADR-0002 §5.2 · §9).

#### 3단계 (선택) — 이전 권한 결정을 지운다

macOS는 한 번 내린 마이크 권한 결정을 기억한다. **이미 허용하거나 거부한 적이 있으면
프롬프트는 다시 뜨지 않으며, 그 상태로는 항목 1을 판정할 수 없다.**

`System Settings › Privacy & Security › Microphone`에서 `Molt Note`가 이미 목록에 있는지 본다.
있다면 **이 앱의 마이크 권한 결정만** 지우고 다시 시작할 수 있다.

```bash
tccutil reset Microphone com.moltnote.app
```

`com.moltnote.app`은 `tauri.conf.json`의 `identifier`다. **이 명령은 이 bundle identifier의
마이크 권한 하나만 지운다** — 다른 앱이나 다른 권한 종류는 건드리지 않는다.
**이 저장소는 이 명령을 실행해 본 적이 없다** [U]. 뜻대로 되지 않으면 System Settings에서
직접 지운다.

#### 4단계 — 앱을 **Finder에서** 실행한다. 터미널에서 띄우지 않는다

아래 명령은 **Finder에서 그 위치를 보여줄 뿐 앱을 실행하지 않는다.**

```bash
open -R "src-tauri/target/release/bundle/macos/Molt Note.app"
```

실행은 Finder에서 **`Molt Note.app`을 더블클릭**한다.

**하지 않는 것** (이유는 §12.1.1):

```text
✗ npm run tauri dev
✗ "…/Molt Note.app/Contents/MacOS/…" 를 터미널에서 직접 실행
```

> 서명되지 않은 로컬 빌드이므로 macOS가 열기를 망설일 수 있다. 그때는 `.app`을
> 우클릭 → **Open**으로 연다.

#### 5단계 — 앱에서 무엇을 누르는가

1. 왼쪽 사이드바에서 **Recording**을 누른다. (앱을 열면 기본 화면은 `Recordings`이며 **다른
   화면이다.** 사이드바 항목은 `Recordings` · `Recording` · `Settings` 셋이다.)
2. 화면 맨 위에 `Phase 2A spike — temporary surface.`가 보인다. 이 화면이 맞다.
3. **Input device** 목록에서 **직접 대고 말할 물리 마이크**를 고른다. 기본 장치가 미리
   골라져 있고 `(default)`로 표시된다. 목록이 비어 있으면 `No input devices found.`가 보이며,
   마이크를 연결한 뒤 **Reload devices**를 누른다.
4. **Capture**의 **Start**를 누른다.
5. 고른 마이크에 대고 **10~20초** 말한다. 상태 표시가 `Recording…`이다.
6. **Stop**을 누른다. 상태가 `Finished`가 되고 **Result**에 네 값이 나온다 —
   `Device` · `File` · `Format` · `Size`.

실패하면 화면 아래에 실패 문장이 그대로 보인다 (§13의 공통 실패 표현). **그 문장을 항목
3·4의 관찰란에 옮겨 적는다.**

**권한 프롬프트가 어디서 뜨는지는 단정하지 않는다** [U] — 이 저장소는 실행해 본 적이 없다.
코드상 마이크에 닿는 지점은 둘이다:

```text
Recording 화면을 열 때   list_input_devices  → cpal의 입력 장치 열거
Start를 누를 때          start_capture       → 고른 장치를 열고 스트림 시작
```

**둘 중 어느 쪽에서 떴는지를 항목 1의 관찰란에 적는다.** 그것이 §5.2가 [H]로 남긴
"열거 자체가 TCC 프롬프트를 유발하는가"에 대한 답이 된다.

#### 6단계 — 출력 파일은 어디에 생기는가

**경로를 추측하지 않는다 — `Result`의 `File` 값이 그 파일의 경로다.**

만들어지는 자리를 코드는 이렇게 정한다 [A✓]:

```text
AppDataDirectory  ( Tauri v2 PathResolver의 app_data_dir )   [R §14.2]
  └─ recordings/                     ( src-tauri/src/platform/app_data_dir.rs )
       └─ capture-<unix seconds>.wav ( src-tauri/src/audio/capture.rs )
```

같은 이름이 이미 있으면 `capture-<초>-2.wav`처럼 비켜 간다 — **앞선 녹음을 덮어쓰지 않는다.**
macOS에서 `app_data_dir`이 어느 경로로 해석되는지는 **이 저장소가 확인하지 않았다** [U].
그래서 아래 명령은 전부 `Result`에서 복사한 경로를 그대로 쓴다.

```bash
FILE="<Result의 File 값을 그대로 붙여넣는다>"
```

#### 7단계 — 크기 · 소리 · 포맷을 확인한다

**크기** (항목 5):

```bash
ls -l "$FILE"
```

화면의 `Size`도 같은 값을 byte로 함께 보여준다 — 화면이 계산한 값이 아니라 **파일시스템에서
읽은 값**이다 [A✓ · §4.2.2]. 0 byte이면 화면이 `The file is empty — nothing was written.`이라고
따로 말한다.

**소리** (항목 6) — 사람이 직접 듣는다:

```bash
afplay "$FILE"
```

또는 Finder에서 그 파일을 더블클릭한다.

**포맷** (항목 7) — 화면의 `Format` 문장을 그대로 믿지 않고 **파일에서 다시 읽는다.**

```bash
afinfo "$FILE"                  # macOS 기본 제공 도구
ffprobe -hide_banner "$FILE"    # ffmpeg가 있는 경우 (§14.1 기준 이 기기는 8.1.1)
```

읽은 값을 이렇게 대조한다.

| 값 | §14.4의 whisper 입력 요구 | 누가 정하는가 |
| --- | --- | --- |
| 컨테이너 | WAV | **코드가 고정한다** [A✓] |
| 비트 심도 | 16-bit 정수 PCM | **코드가 고정한다** [A✓] |
| 샘플레이트 | 모델은 16000 Hz 기준 | **장치가 정한다** — 리샘플링이 없다 (§4.2.3) |
| 채널 | 모델은 mono 기준 | **장치가 정한다** — 다운믹스가 없다 (§4.2.3) |

> **샘플레이트·채널이 어긋나는 것 자체는 결함이 아니다.** 그것이 뜻하는 바는
> **리샘플링/다운믹스 책임이 어딘가에 생긴다**는 것이며, 어디에 둘지는 §11이 Phase 3으로
> 미뤄 둔 결정이다. 다만 §6의 근거 1이 말하는 "변환 없이"는 그만큼 약해진다 —
> **그 사실을 항목 7의 관찰란에 그대로 적는다.**
> 반대로 **컨테이너나 비트 심도가 어긋났다면** 그것은 코드가 고정한 값이 지켜지지 않은
> 것이므로 성격이 다르다. 그때는 §6.1의 네 번째 반증 조건이다.

**손상 여부** (항목 8): 위 도구들이 파일을 읽고 **재생 길이가 실제 녹음한 시간과 비슷하게**
나오면 헤더가 확정된 것이다. WAV(RIFF)는 길이를 헤더에 갖는 포맷이므로 확정되지 않은 파일은
여기서 드러난다 (§5.5). 앱을 다시 열지 않은 상태에서 확인한다.

#### 8단계 — 결과를 §12의 표에 적는다

8개 항목의 `결과`를 `PASS` 또는 `FAIL`로 바꾸고 관찰란을 채운다. 표 위의 네 줄(확인 일자 ·
확인한 사람 · 빌드한 커밋 · 기기)도 채운다. 그다음은 §12.2가 정한다.

### 12.1.1 왜 터미널 실행이나 `tauri dev`로는 부족한가

세 가지가 각각 독립된 이유이며, 하나만으로도 번들 실행이 필요하다.

| | |
| --- | --- |
| **1. macOS 권한은 실행 주체에 귀속된다** | 터미널에서 앱을 띄우면 마이크 권한 결정이 **터미널 앱**에 붙는다. 그러면 확인한 것은 "터미널이 마이크를 쓸 수 있다"이지 **제품이 겪을 상황이 아니다** [R §14.3 · `phase-prompt/02a-recording-engine-validation.md`]. 항목 1·2·3이 전부 이 위에 서 있다 |
| **2. dev 실행에는 알려진 이슈가 있다** | Tauri **#11951**(open) — **dev 실행에서 마이크 권한 프롬프트가 뜨지 않는다** [R §14.3]. 즉 `npm run tauri dev`에서 프롬프트를 보지 못했다는 사실은 항목 1에 대해 **아무것도 말해 주지 않는다** |
| **3. 병합된 `Info.plist`는 번들에만 있다** | `NSMicrophoneUsageDescription`은 `src-tauri/Info.plist`에 있고 Tauri CLI 생성값과 **번들을 만들 때 병합된다** [R §14.3 · ADR-0002 §4]. 항목 1이 보려는 **프롬프트 문구**는 번들된 `.app` 안에만 존재한다 |

**그래서 §12.1은 `npm run tauri build` → Finder 더블클릭 경로만을 적었다.**

이 spike가 그 경로로 실행 가능하다는 것은 저장소 구조에서 나온다 [A✓]:
캡처가 Tauri command 뒤에 있고(`list_input_devices` · `start_capture` · `stop_capture`가
`src-tauri/src/lib.rs`에 등록되어 있다), 그 화면이 앱 안의 `Recording` 라우트로 등록되어
있으므로(`src/screens/registry.ts`), **번들된 앱 하나만으로 §12.1의 5단계를 지날 수 있다** —
별도의 실행기도, dev 서버도, 개발자 도구도 필요하지 않다.

> 다만 **"실행 가능한 구조다"와 "실행해 봤다"는 다르다.** 후자는 §12의 표가 채워질 때
> 처음 사실이 된다 (§4.2.4).

### 12.2 결과를 어디에 적는가

8개 항목의 결과는 **이 문서 §12의 표에 사람이 직접 적는다.**

| 결과 | 그다음 |
| --- | --- |
| **8개가 전부 `PASS`** | §12의 표 위에 확인 일자를 남기고, 상단의 `Status`를 확정 표기로 바꾼다. 그때 Phase 2B를 시작할 수 있다 |
| **하나라도 `FAIL`** | §6.1의 반증 조건에 따라 잠정 선택을 다시 연다. **Phase 2B를 시작하지 않는다.** 어느 반증 조건에 걸렸는지를 함께 적는다 |
| **판정할 수 없었다** | `PENDING`으로 되돌리고 무엇이 막았는지 적는다. **모르는 것을 `PASS`로 적지 않는다** (§3) |

> **Worker나 Gate가 이 표를 대신 채우지 않는다.** 자동 Gate가 전부 green이라는 사실은
> §4.2가 적은 범위에 대한 것이며, 이 표의 어떤 칸에 대해서도 증거가 되지 않는다.

---

## 13. Consequences

- **Phase 2B는 이 문서가 확정되기 전에 시작하지 않는다.** §12가 관문이다.
- 잠정 선택이 유지되면 `src-tauri/Cargo.toml`에 `cpal`·`hound`가 추가되고
  프로젝트 MSRV가 1.85 이상이 된다 [R §14.3].
- 캡처 책임이 Rust 경계 안에 놓이므로 저장소(ADR-0001) · Ollama 호출 방향(§14.5)과
  **외부 자원 접근 주체가 갈리지 않는다.**
- 오디오 관련 실패를 표현하려면 `FailureKind` 확장이 필요하다. 그 기능을 만드는 Task가
  함께 추가한다 (§9).
- **이 문서가 확정되지 않은 채로 인용되면 안 된다.** 다른 문서·Task가 이 결정을
  "결정된 것"으로 전제하면 그것은 §6.1이 막으려 한 바로 그 실패다.

## 14. 이 결정이 다루지 않는 것

- 완성된 Recording 화면 UX · 전체 pause/resume lifecycle · 재시작 영속성 · production playback ·
  장시간 녹음 테스트 · 전체 실패 UX · Recording DB 영속화 파이프라인 — **전부 Phase 2B다.**
- whisper 통합 · 전사 · AI Provider · Notion · Markdown export — Phase 3 이후.
- Windows 빌드 · 실행 · 권한 로직 — Phase 6. 이 문서는 Windows를 **평가 근거로만** 다뤘다 (§10).
- macOS entitlements · 코드 서명 · 공증 — ADR-0002 §7과 같은 이유로 여기서도 다루지 않는다.
